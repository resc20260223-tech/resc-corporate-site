v3.0-01

使っている技術

TECH STACK

技術は5つの区分で持っています。フロントエンド、バックエンド、インフラ、データ、開発基盤。トップページでは名前だけを並べましたが、この版では区分ごとに「なぜそれを使うか」と「案件によって変わるところ」を書き足しました。

MANIFEST — NEXTGRID v3.05 GROUPS

front フロント

TypeScriptReactNext.jsVue.jsHTML / CSS

back バックエンド

Node.jsPHP / LaravelPythonREST APIGraphQL

infra インフラ

AWSDockerTerraformLinuxCDN

data データ

PostgreSQLMySQLRedisObject Storage集計用のデータ基盤

devops 開発基盤

Git / GitHubGitHub ActionsJestPlaywrightエラー監視Slack / Notion

ここに挙げたものを、すべての案件で使うわけではありません。何を使うかは、すでに動いている仕組み・運用する方・引き継ぎのしやすさを見て、相談の段階で一緒に決めます。ご指定のものがある場合は、それに合わせます。

ひとつの機能は、利用者の画面（front）から、業務のルールを持つサーバー（back）を通って、データ（data）に届きます。その道すじの外側で、インフラ（infra）が動かす場所を用意し、開発基盤（devops）が変更とテストと監視を受け持ちます。

FIG.v3.0-01 — REQUEST PATH図は区分の関係をイメージで表したものです

  • ひとつの機能が通る道すじ（画面 → サーバー → データ）
  • その道すじを支える区分（インフラ・開発基盤）

  • front

    フロントエンド

    TypeScript / React / Next.js / Vue.js

    • −よくある状態：画面をひとつ直すたびに、どこに影響が出るか分からず、確認に時間がかかる
    • +やっていること：型のある言語（TypeScript）で書き、画面を部品に分けて、直したときに影響する範囲を読めるようにしています
    • +やっていること：キーボードだけで操作できるか、読み上げで意味が通るかを、つくりながら確認しています
    • +案件で変わるところ：React と Vue.js のどちらを使うかは、すでにある画面と、あとで触る方に合わせて決めます

  • back

    バックエンド

    Node.js / PHP・Laravel / Python / REST API / GraphQL

    • −よくある状態：業務のルールが画面ごとに書かれていて、同じ処理が何か所にも散らばっている
    • +やっていること：業務のルールはサーバー側に集め、画面からは API を通して呼ぶ形にしています
    • +やっていること：すでに動いている販売管理や会計の仕組みとは、API かファイルの受け渡しでつなぎます
    • +案件で変わるところ：言語は、社内で引き継げるか・既存の環境で動かせるかを見て選びます

  • infra

    インフラ

    AWS / Docker / Terraform / Linux / CDN

    • −よくある状態：動かしている環境の中身が誰にも分からず、手を入れられないまま止まっている
    • +やっていること：環境の構成はコード（Terraform）と Docker で残し、同じものを作り直せる状態にしています
    • +やっていること：検証環境と本番環境を分け、同じ手順で配信できるようにしています
    • +案件で変わるところ：規模が小さいうちは構成も小さく組みます。使っていないものを増やしません

  • data

    データ

    PostgreSQL / MySQL / Redis / オブジェクトストレージ

    • −よくある状態：同じ情報が複数のファイルに散らばっていて、どれが正しいのか決められない
    • +やっていること：どこを正とするかを先に決めてから、データの持ち方をつくります
    • +やっていること：集計は業務用のデータベースと分けて、重い処理が日々の業務を止めない形にします
    • +案件で変わるところ：扱う量と更新の頻度によって、置き場所と持ち方が変わります

  • devops

    開発基盤

    Git・GitHub / GitHub Actions / Jest・Playwright / エラー監視

    • −よくある状態：誰がいつ何を変えたのかが残っておらず、不具合が出ても戻す先が分からない
    • +やっていること：変更はすべて Git に記録し、テストと配信は GitHub Actions で自動的に走らせています
    • +やっていること：エラーは監視の仕組みで受け取り、気づいてから直すまでの時間を短くしています
    • +案件で変わるところ：やりとりの場所（Slack・Notion など）は、ご利用中のものに合わせます
これらを実際にどう組み合わせたかは、事例の詳細で v2.1  導入事例 詳細  →
v3.0-02

1案件を、どう進めているか

TEAM

1案件あたり3〜4名です。テックリード1名、実装1〜2名、ディレクション1名。窓口は1人に固定します。相談から決定までに挟まる人が少ないほど、確認の往復も手戻りも減るためです。

TEAM INDEX
項目やっていること
チーム構成1案件あたり3〜4名（テックリード1／実装1〜2／ディレクション1）。窓口は1人に固定します
進め方2週間をひと区切りにして、区切りごとに動くものをお見せします。仕様書だけで進めません
定例週1回。決まったこと・決まっていないことを、その場で書き出して共有します
レビュー変更はすべてプルリクエストにして、別のメンバーが読んでからマージします
テスト自動テスト（ユニット／画面操作）と、リリース前の手動確認を組み合わせます
リリース検証環境で確認してから本番へ。切り戻しの手順を用意しておきます
運用リリース後は月次で状況を見て、直すもの・足すものを次の版に入れます

案件の規模によって人数は前後します。担当を増やすときも、窓口は同じ1人のままにしています。

  • −よくある状態：できあがるまで中身が見えず、最後に「思っていたものと違う」となる
  • +やっていること：2週間ごとに、動くものをそのまま見ていただきます。認識のずれをその都度つぶします
  • +やっていること：決まっていないことも定例で書き出して、決めきれないまま次に進んでいる箇所を見えるようにします

※写真はイメージです。これはRESCが作成したサンプルサイトのため、実在の拠点・担当者を示すものではありません。

v3.0-03

変更が本番に届くまで

DELIVERY

書いたコードは、そのまま本番には出ません。プルリクエストにして別のメンバーが読み、自動テストが通り、検証環境で確認してから本番に出します。出したあとに問題が見つかったときのために、前の版へ戻す手順も先に用意しておきます。

変更は、書く（EDIT）、プルリクエストにしてレビューを受ける（REVIEW）、自動テストを走らせる（CI TEST）、検証環境で確認する（STAGING）、本番へ出す（PROD）の順に進みます。本番で問題が見つかったときは、切り戻し（ROLLBACK）で前の版に戻してから直します。

FIG.v3.0-02 — DELIVERY図は手順の順番をイメージで表したものです

  • 変更が本番に届くまでの一本道
  • 前の版へ戻す経路（切り戻し）
DELIVERY INDEX
段階やること使っているもの
01 EDIT変更を書く。作業用の枝を切ってから手を入れますGit・GitHub
02 REVIEWプルリクエストにして、別のメンバーが読んでからマージしますGitHub
03 CI TESTユニットテストと画面操作のテストを自動で走らせますGitHub Actions・Jest・Playwright
04 STAGING検証環境に出して、実際の手順どおりに手で確認しますDocker・検証環境
05 PROD本番へ出します。出したあとはエラー監視で様子を見ますAWS・エラー監視
ROLLBACK問題が見つかったときは前の版に戻してから、原因を直します配信の履歴・バックアップ

自動テストですべての不具合を見つけられるわけではないので、リリース前の手動確認と組み合わせています。テストをどこまで書くかは、止まったときの影響の大きさを見て決めます。

v3.0-04

セキュリティで行っていること

SECURITY

お預かりするのは、お客さまの業務のデータです。ここでは、私たちが実際に行っている対策をそのまま並べます。書いていないことはやっていない、と読んでいただいて構いません。

SECURITY INDEX
区分行っていること
アクセス管理権限は担当する範囲に限ります。管理画面には多要素認証を設定し、担当を離れたときに権限を外す手順を決めています
データの取り扱い通信を暗号化（TLS）し、保管するデータも暗号化します。本番のデータをそのまま開発環境に持ち出しません（要るときは値を伏せて使います）
秘密情報接続情報と鍵はソースコードに書かず、専用の保管先で管理しています
バックアップ日次でバックアップを取り、復旧の手順を定期的に確認しています
脆弱性対応使っているライブラリの更新情報を定期的に確認し、影響のあるものから対応しています
事故が起きたとき連絡の順番と一次対応の手順をあらかじめ決めて、共有しています

対策の範囲は、お預かりするデータの種類とご要望によって変わります。契約の前に、どこまでを私たちが受け持つかを書面で分けたうえで進めています。

リスクをゼロにはできない前提で、
気づける・戻せる形にしています。

対策を積んでも、起きる可能性は残ります。だから私たちは、起きたときに気づける仕組み（監視・記録）と、戻せる手順（バックアップ・切り戻し）を先に用意しておくほうに手をかけています。
